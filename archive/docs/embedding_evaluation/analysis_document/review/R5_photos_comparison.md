Reviewer pass over ANALYSIS.md §0, §3, §4 (context), §5, §6, checked against
`EVTOLNEWS_DS/3_embedding_evaluation/embedding_analysis_registers/` (incl.
`EVTOLNEWS_EMBEDDING_ANALYSIS_REGISTERS.md` and its `tables/`), `1639_LABELLED/

`fairness_class_counts.csv`), `crop_experiment/RESULTS.md`, and the
`analysis_document.py` code that builds §6's class-mix test. All numbers

**F5.1 [MUST]** · §6, Table 21/22 · The label mismatch between the two sources is never restated where the comparison is actually made · §1.3 discloses that the directory's own class agrees with the codebook's G1 parent for only 83 of 99 linked aircraft (16% disagreement). §6 then compares "drawings (G1 folded to parent)" against "photos (directory class)" as if the two were the same target variable, with no reminder of that ~16% mismatch. Since the whole point of §6 is "which source's label is recovered better," a labelling scheme that disagrees with the other source's scheme on 1 in 6 aircraft is a first-order confound for that claim, not a footnote to file 500 lines earlier. · A reader who reaches §6 without perfect recall of §1.3 will read "photos score higher" as a clean medium comparison, when part of the gap could be the photos being scored against an easier/different target than the drawings. · Add one sentence at the start of §6 (or a footnote on Table 21) restating the 83/99 agreement rate and noting that "which source carries more" is therefore also partly "which label scheme is easier to recover." · Cost: doc edit only, no recompute.

**F5.2 [MUST]** · §0 Table 1, §6, §8 · The class-mix result — the section's most consequential finding — is not given the prominence its consequence deserves, and the author's own open question (§10) about this is left unresolved in the delivered text · §0's summary table states "Photos score higher... but with the drawings' class mix the photos score 0.46: the gap is mostly the pool" as a subordinate clause after a semicolon. §6 itself leads with the full-pool colour/greyscale comparison (+0.12/+0.13) and only several paragraphs later introduces the matched test that says most of that advantage is an artifact of pool size and mix. §10 explicitly asks "keep the full-set comparison as the headline... or make the matched comparison the headline?" — i.e. the author knows this is unresolved and the document as reviewed still has it unresolved. · This is not a minor wording choice: the matched result changes the finding from "the medium (photographs) helps recognition" to "the medium is not shown to help, once the pool is comparable" — a materially different claim for the thesis's RQ4 answer. Leaving it as a footnote risks the thesis (or a reader skimming §0/§8) walking away with the wrong headline. · Resolve open question N-photo-mix explicitly: make the matched comparison (0.46 vs 0.44) the number that answers "which source carries more," and keep the raw full-pool number (0.56 vs 0.44) as the "before controlling for pool" context, in that order, in §0, §6 and §8 alike. · Cost: doc edit only — all numbers already computed and in the document.

**F5.3 [MUST]** · §6, Table 22 · "Lies inside the range of the draws" is an eyeball-inclusion check, not a formal test of the matched-photos-vs-drawings difference · Table 21 reports photos−drawings with a proper joint bootstrap CI ([+0.027, +0.211]). Table 22 does not do the equivalent for the matched comparison: it only reports the matched-photo mean and the [2.5, 97.5] percentiles of the 200 draws, then checks by eye that the drawings' fixed score (0.445) falls inside that range. That is a weaker claim than a CI on the difference — a wide "inside the range" band can hide a real, smaller, but nonzero gap, and "not rejected" is being read as "not shown to carry more," which needs the sharper test to be safely stated as strongly as it is. · The conclusion "the medium is not shown to carry more architecture" is the section's headline claim (see F5.2); it deserves the same rigor as the +0.12 claim it is meant to qualify. · Compute a matched-photos − drawings difference with a combined interval (e.g. resample drawings' own bootstrap alongside the 200 class-mix draws, or report the two-sided p-value of drawings' score against the draw distribution) and report that CI next to Table 22, replacing or supplementing "lies inside the range of the draws." · Cost: CPU recompute — reuses the already-computed similarity matrix and the 200 draws already produced by `class_mix_matched()` in analysis_document.py; no GPU needed.

**F5.4 [SHOULD]** · §5.3, §6 · The one confound test that speaks most directly to "is the photo advantage fair" — removing the background — is run on the base model only, and its result is never brought into §6 · §5.3 states plainly that the crop test used dinov2-large (base), "before the registers model was adopted; it is the one result of this document on base," which is honest disclosure. But the chosen model for every other number in §5 and §6 is the registers model, and the crop-vs-original difference has not been re-measured on it. §6's fairness argument (colour/greyscale control, class-mix control) never mentions the background control at all, even though "photos carry backgrounds that drawings do not" is exactly the kind of unfairness §6 should be checking. · If the registers model's late-layer attention (which is more spread out per Table 8/Figure 4) reads more of the background than the base model did, the base-model crop test could understate a real registers-model background contribution — a gap in the one place this needs to be airtight. · Re-run the crop embedding extraction with the registers model on the already-existing 518px crops (`2_embedding_extraction/crop_experiment/processed/518/`), recompute the paired kNN difference, and add one sentence to §6 referencing it as a third fairness control alongside colour/greyscale and class-mix. · Cost: GPU recompute (crops are already detected and processed; only the embedding extraction + eval step needs to run, ~equivalent to the ~20 min the base run took per crop_experiment/RESULTS.md).

**F5.5 [SHOULD]** · §2.5, §6 Table 21 · Greyscale is called "the fairness check" but it only controls for colour, not for the other systematic style differences between photographs and line drawings · §2.5: "The greyscale run doubles as the fairness check of §6." Converting a photo to greyscale removes chrominance but leaves shading, gradients, photographic texture, depth-of-field blur, and backgrounds untouched — all of which a patent line drawing on white paper has none of. Calling this single control "the fairness check" (definite article) implies it addresses fairness broadly, when it only rules out one specific candidate confound (colour). · A reader could take "it's not colour" as "the comparison is fair," which overstates what the test shows; the real fairness case for §6 rests on colour + class-mix (+ ideally background, F5.4), not colour alone. · Reword to "a fairness check" (not "the"), and in §6 explicitly list it as one of two (or three, with F5.4) controls, each targeting a specific candidate confound, rather than implying it settles fairness on its own. · Cost: doc edit only.

**F5.6 [SHOULD]** · §6.1, §9 · The 94 matched patent aircraft are not a representative sample of the 663-aircraft drawing corpus, and this is not acknowledged anywhere · Only patent aircraft that happen to have an evtol.news directory page can enter the matching test. Spot-checking `matching_ranks.csv` shows these are large, well-covered, named programmes (Joby, Lilium, CityAirbus, Porsche-Boeing, etc.) — aircraft that are famous enough to be written up by an industry news site, which correlates with being built, well-funded, and often visually distinctive. This is a plausible reason the model can link them "well above chance" (48% top-50) that would not extend to an average, less-publicized patent in the other 569 aircraft. §9 Limitations lists small classes, the filter audit, line thickening, labels, and the frozen model, but not this selection effect on §6.1's matching sample. · The matching result is presented in §0 and §8 as a general capability ("above chance, not reliably") without the caveat that it was only ever tested on the most prominent, best-documented subset of the corpus — the one subset where matching should be easiest. · Add a bullet to §9 noting the matched 94 are systematically the more prominent/covered aircraft in the corpus, and soften the §0/§8 headline phrasing accordingly (e.g. "for the subset of patent aircraft covered by the directory"). · Cost: doc edit only.

**F5.7 [SHOULD]** · §6.1, Table 23 · Unexplained discrepancy: the photo→patent gallery is 665 drawing aircraft, but the drawing corpus is 663 everywhere else in the document · §1.1, Table 15, Table 18, Table 21 and Table 22 all use 663 aircraft for the drawings. Table 23's photo→patent row reports `gallery = 665`. The same 665 (vs. 663) also appears in Table 8 (§2.2, outside this review's scope but the same discrepancy). Nothing in the text explains the 2-aircraft difference (e.g. whether it is a pre-final-filter snapshot, or duplicate main figures). · A careful reader who cross-checks Tables 15/21/22/23 will hit an unexplained inconsistency in the corpus size that undermines confidence in the "one number, one meaning across the document" claim made in §3 ("the same number... means what the same number means in the other"). · Track down why the matching gallery is 665 (likely a build-time snapshot before the 2 unclassifiable aircraft were dropped, per §1.1) and either fix it to 663 or add a one-clause explanation next to Table 23. · Cost: CPU check against the matching pipeline's aircraft list (already-computed data, no GPU).

**F5.8 [COULD]** · §1.3 vs §6.1 · The 99 linked patent aircraft of §1.3 becomes 94 in §6.1's matching test, with no stated reason · §1.3: "On the 99 patent aircraft that have a directory page..."; §6.1: "For the 94 patent aircraft that have a directory page, the main figure queried..." A plausible explanation is that some of the 99's own hero image was itself one of the line drawings removed from the gallery (so their own page can never appear in the ranking and they were excluded as queries), but the document doesn't say so. · Minor, but it's the kind of unexplained number drift a supervisor will circle. · Add a half-sentence: "(5 of the 99 are excluded because their own hero image is a line drawing removed from the gallery)" or whatever the actual reason is. · Cost: CPU check + doc edit.

**F5.9 [SHOULD]** · §5.2, §6 · The maturity-status confound found in §5 is never connected to §6's medium-fairness discussion · §5.2 (T6) finds that the built/concept status on the directory page moves the photo vectors more than architecture in 4 of 6 matrices — a substantial, layer-dependent confound internal to the photo set. §6 discusses colour/greyscale and class-mix as fairness controls but never asks whether maturity (which drawings, being patent filings, don't carry an equivalent signal for) is part of why photos separate classes better. Some classes (e.g. Wingless/Multicopter, largely hobbyist-built) plausibly skew more "built" than others (e.g. Vectored Thrust, dominated by concept renders), which would let a maturity-correlated visual cue masquerade as an architecture signal in the photo kNN. · If maturity is partly riding along with class in the photo embedding, part of photos' "better" per-class recall (Table 22, e.g. WM at 0.74) could be maturity, not architecture — directly relevant to the §6 question but currently unexamined. · At minimum, cross-reference §5.2's finding in §6 as an open confound specific to the photo side; if time allows, check whether maturity status correlates with directory class (a simple crosstab, already-available data) and report it. · Cost: doc edit (cross-reference) is free; the crosstab check is CPU-only using data already on disk (directory maturity field + class label).

**F5.10 [SHOULD] (missing graph)** · §5.3 · The photo image-rule test (hero / random-other / mean-of-all) is reported as one prose sentence with a single combined interval width, while the equivalent drawings test (§4.5) gets a full table with per-rule 95% CIs (Table 18) and a figure (Figure 7) · §5.3: "the image rule matters as little as on the drawings: hero image 0.563, one random other image 0.521, the mean of all kept images 0.578, against an interval about 0.06 wide for one rule." This drops the per-rule CIs and the "which layer/pooling" breakdown entirely. The source data already exists with full precision: `EVTOLNEWS_EMBEDDING_ANALYSIS_REGISTERS.md` Table 11 (per-matrix, per-rule kNN) and Figure 8 (`figs/f05_rules.png`, markers + 95% CI whiskers per rule) in the registers report. · This is an avoidable asymmetry: the reader can audit the drawings' T7 claim from the document itself but has to go find the registers report to audit the photos' T7 claim, even though both are "does the image choice matter" questions the document treats as parallel. · Add a table (mirroring Table 18's format: rule, kNN-5, 95% CI) for the three photo image rules at L24 CLS, and either copy in `f05_rules.png` or build the ANALYSIS.md-styled equivalent (`f_matching`/`f_five_class` conventions). Both the table and the figure already exist in the registers report and just need porting. · Cost: already in saved results — no recompute, just copy/reformat.

**F5.11 [COULD] (missing graph)** · Figure 14 (`f_five_class.png`) · The per-class "photos, drawings' class mix" bars carry no uncertainty indicator, while the aggregate balanced-accuracy bar does · The figure shows a whisker on the grey "balanced accuracy" matched bar but none on the five pale per-class matched bars, even though each is also a mean over the same 200 draws and is subject to potentially large variance for classes with the biggest pool-size swing under resampling (e.g. WM drawn at n=50 out of 332 available each draw). A reader can't tell from the figure whether, say, WM's matched recall of 0.43 is a tight estimate or a wide one. · `class_mix_matched()` in `analysis_document.py` already computes `recs` (per-draw, per-class recall) before collapsing to the mean (`np.mean(recs, axis=0)`); the percentiles needed for whiskers are one line away. · Store the [2.5, 97.5] percentiles per class alongside the existing mean in `class_mix_matched()`'s return dict, and add whiskers to the five pale bars in `fig_five_class()`. · Cost: CPU recompute — `recs` is already generated in the existing run, this only adds an aggregation step and a re-plot; no GPU needed.

**F5.12 [MUST] (organisation)** · §6 · §6 does not open on the fairness question it is actually answering, and its controls are scattered across three different sections · The section header is "Drawings against photographs," and the opening paragraph is a protocol restatement ("The comparison uses the same model, the same readout..."), not a framing of the actual question the section spends most of its length on: is this a fair comparison, given the two sources differ in colour, background, size, and class balance? The three controls that answer that question are split up: colour/greyscale is set up in §2.5 (a different chapter section, about setup selection) and only its result appears in §6; the background/crop control is entirely in §5.3, several pages before §6, on a different model (F5.4); only class-mix is native to §6. A reader has to assemble the fairness case for §6 from three non-adjacent places. · This works against the section doing what its own open question (§10, N-photo-mix) implies it should do: state the fairness question, answer it with all controls together, and land on one conclusion. As it stands the section reads as "here's the raw gap" followed by "oh, but also here's a mitigating factor," rather than a designed fairness test. · Open §6 with an explicit framing sentence (e.g. "Is the photo advantage real, or an artifact of how the two sources differ — colour, background, and class mix?"), then present colour/greyscale, background crop (moved/cross-referenced per F5.4), and class-mix together as the three controls, and close with one paragraph giving the answer (which should also absorb F5.2's resolution of the headline-number question). Keep §6.1 (identity matching) as a clearly separate sub-question after that close (see F5.14). · Cost: doc restructure only, no recompute (all component results already exist somewhere in the document).

**F5.13 [COULD] (organisation)** · §0, §6, §8 · The same "0.56 vs 0.44, matched 0.46" result is stated three times with three different hedges · §0 Table 1: "the gap is mostly the pool." §6 own text: "on this evidence the medium itself is not shown to carry more architecture." §8 Conclusions: "an advantage that shrinks to nothing measurable once the photo pool has the drawings' size and class mix." Each phrasing is defensible on its own, but three different formulations of the same qualifying clause across the document reads as if the author kept rewording it without settling on one, which is consistent with §10 flagging this exact point as still open. · Minor on its own, but it compounds F5.2: until the headline-vs-qualifier question is resolved, the wording will keep drifting. · Once F5.2 is resolved, pick one sentence for the qualifying clause and reuse it verbatim (or near-verbatim) in §0, §6 and §8. · Cost: doc edit only.

**F5.14 [COULD] (organisation)** · §6.1 · The same-aircraft matching subsection has no transition marking that it is a different question from the medium-fairness comparison above it · §6 up to that point is about whether photos "carry more architecture" than drawings (a fairness/accuracy question); §6.1 is about whether a single aircraft's drawing and photo can be linked to each other (an identity/retrieval question). These are related but distinct, and the section header ("6.1 The same aircraft in both sources") doesn't signal the shift; it reads as a continuation of the class-mix discussion just above it. · A reader following §6's fairness argument can lose the thread when the subject changes from "which source reads architecture better" to "can the model find aircraft X's photo from its patent drawing." · Add one preamble sentence to §6.1 explicitly marking the change of question, e.g. "A different question: can the model link a specific aircraft's drawing to its own photograph, rather than just its class?" · Cost: doc edit only.
